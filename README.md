# عبود Trading Controller — v22 Beta App HTTP

## ابدأ من هنا: إعداد Render قبل الرفع والتشغيل

هذا الإصدار يضيف مسار HTTP بدلاً من نقر المتصفح لتطبيق `@signal_meta_bot`، ويبقي ملفات تنفيذ الصفقات والجلسات والتدبيل والجدولة وقاعدة البيانات كما في أرشيف v21. أضيف AUD/CAD OTC كخيار تكميلي في لوحة التحكم والتحقق من الإعدادات، دون تغيير ترتيب الأزواج الثلاثين أو ترحيل اختيارك المحفوظ. لا يحتاج Chromium في مسار HTTP الافتراضي الموصى به. تعليمات v20/v21 الموجودة لاحقًا سجل سابق، وهذا القسم هو المرجع للتشغيل الحالي.

**حدود التحقق:** تحققت نقاط النهاية وأسماء الحقول من ملف JavaScript العام الفعلي للمزود، بالإضافة إلى لقطات bootstrap المرفقة. اختبارات الشبكة تشغّل خادم aiohttp محليًا يحاكي عقد المزود، وليست اتصالاً مصادقًا بحساب المستخدم. لم تُستخدم قيم initData/session_id/action_token التي ظهرت في المحادثة، ولم تُفتح أي صفقة حية. نجاح الاختبارات ليس ضمان ربح أو ضمان توافق كل بطاقة مستقبلية للمزود. لم نعد نفترض أن غياب Socket في لقطة يثبت عدم استخدامه مطلقًا؛ المسار الذي وثّقناه وعليه هذا الإصدار هو HTTP.

### 1. المتغيرات المطلوبة في Render

لخدمة Render القائمة يدويًا: حدّث Environment بنفسك قبل إعادة النشر؛ رفع render.yaml لا يغيّر إعدادات خدمتك اليدوية تلقائيًا. إذا كنت تستخدم Blueprint فالقيم مضافة في الملف. لا تنشئ خدمة ثانية متزامنة بنفس توكن التحكم والجلسة وقاعدة البيانات.

| المتغير | القيمة الموصى بها قبل الاختبار | السبب |
|---|---|---|
| `SIGNAL_BOT_USERNAME` | `@signal_meta_bot` | بوت مصدر الإشارات، وليس بوت التحكم |
| `META_SIGNAL_BACKEND` | `http` | مسار صارم: لا يتحول إلى متصفح أو رسائل تلقائيًا عند الفشل |
| `META_API_BASE` | `https://sdasdsahdsa.lol/miniapp/api` | الأصل الذي ظهر في اللقطات وملف الواجهة العام |
| `META_BOT_ID` | `8808473133` | معرّف بوت المزود، وليس Telegram ID الخاص بك |
| `META_DRY_RUN` | `1` | يقرأ إشارة واحدة ثم يوقف الحلقة دون إرسال أي أمر تداول |
| `META_DEVICE_LANGUAGE` | `ar-YE` | تلميح لغة الجهاز كما في اللقطة، لا يغير لغة حسابك قسرًا |
| `META_POLL_SECONDS` | `0.5` | استطلاع محافظ؛ الواجهة الحالية تستعمل 75/150ms أثناء الانشغال |
| `META_HTTP_TIMEOUT_SECONDS` | `12` | مهلة الطلب المفرد |
| `META_OPERATION_TIMEOUT_SECONDS` | `45` | مهلة انتهاء عمليات الملاحة |
| `SIGNAL_TIMEOUT_SECONDS` | `45` | مهلة انتظار نتيجة الإشارة في المستمع القائم |
| `DURATION_SECONDS` | `60` | قيمة بدء لقواعد بيانات جديدة فقط؛ لا تهاجر إعدادًا محفوظًا |

**احتفظ دون تغيير** بـ CONTROL_BOT_TOKEN وADMIN_TELEGRAM_ID وTELEGRAM_API_ID وTELEGRAM_API_HASH وTELEGRAM_STRING_SESSION وMONGO_URI وDB_NAME وبيانات حسابات المنصة المحفوظة. لا تضف متغير initData ولا session_id ولا action_token ولا operation_id. تُستخرج بيانات فتح التطبيق تلقائيًا من جلسة Telethon القائمة، ولا يحدث تسجيل دخول تفاعلي أو كتابة ملف جلسة جديد. حدّث اسم مصدر الإشارات القديم إن كان ما زال موجودًا في Environment لأن المتغير المخزن يتقدم على القيمة الافتراضية في config.py.

**مهم جدًا:** إذا كانت المدة محفوظة في MongoDB على 5 ثوانٍ فلن يغيّرها DURATION_SECONDS=60. اختر من إعدادات بوت التحكم M1 / 60 ثانية وزوج OTC متاحًا مثل AUD/CAD قبل الاختبار. لا يغيّر هذا الإصدار قاعدة البيانات تلقائيًا ولا يحوّل S5 المقفلة إلى M1 دون اختيارك. إذا كان الحساب المختار محفوظًا REAL فلا يجعله ACCOUNT_TYPE=PRACTICE تجريبيًا تلقائيًا؛ بدّل إلى PRACTICE من لوحة التحكم صراحة.

### 2. أوامر خدمة Render

Build Command:

```sh
pip install -r requirements.txt && python meta_preflight.py
```

Start Command كما هو:

```sh
python -u run.py
```

المجلد الجذر للخدمة هو المجلد الذي يحوي run.py وrequirements.txt (داخل الأرشيف: po_autotrader). أبقِ Health Check على `/health`. لا تضع أمر الجلسة أو طلب الإشارة في Build Command. فحص البناء الافتراضي محلي تمامًا ولا يتصل بتيليجرام أو المزود أو MongoDB.

لا يحتاج هذا المسار أمر `playwright install chromium` أو متغير PLAYWRIGHT_BROWSERS_PATH. يمكن إزالة متغير المتصفح القديم من إعداد الخدمة ما دمت تستخدم META_SIGNAL_BACKEND=http. لا تغيّر التوكنات ولا أسرار الاتصال أثناء ذلك.

### 3. الفحص المرحلي قبل التداول

1. شغّل `python meta_preflight.py`: فحص إعدادات دون شبكة ودون صفقات. لا يثبت صلاحية الأسرار أو وصول حسابك للمزود.
2. اختياريًا من Render Shell والخدمة متوقفة عن التداول: `python meta_preflight.py --live` يفحص اتصال جلسة تيليجرام الحالية وbootstrap/status فقط، دون طلب إشارة أو اتصال بمنصة التداول. لا تشغّله بالتوازي مع عملية تداول نشطة.
3. لاختبار إشارة واحدة دون منصة التداول: `python meta_preflight.py --live --request-signal --asset AUDCAD_otc --duration 60`. يشترط META_DRY_RUN=1، ويستهلك طلب إشارة فعليًا لدى المزود وقد يُحتسب من حصتك. لا يقرأ SSID ولا يفتح اتصال Pocket Option ولا يكتب في MongoDB. سيظهر META_DRY_RUN_COMPLETE عند النجاح.
4. أو بعد النشر، اختر PRACTICE والزوج والمدة في بوت التحكم ثم Start مع META_DRY_RUN=1. يتوقف مسار العامل بعد قراءة نتيجة واحدة ويظهر تنبيه الاختبار. هذا الوضع لا يرسل أوامر تداول جديدة، لكنه ليس محاكاة محلية للمزود: طلب الإشارة حقيقي وقد يستهلك حصة. اختيار الزوج/المدة أثناء توقف البوت قد يحضّر إشارة أولى طبقًا لسلوك المشروع الأصلي.
5. بعد التحقق من الاتجاه والتطابق، غيّر META_DRY_RUN إلى `0` وأعد النشر، وأبقِ الحساب PRACTICE لاختبار دورة Get signal ثم New signal وتغيير الزوج/المدة. التداول الحقيقي يحتاج اختيارًا واعيًا منك لاحقًا؛ لا نفعّله تلقائيًا.

### 4. ما ينفذه الربط

يدخل عبر قائمة Beta App الفعلية أو زرها، ثم يطلب رابط WebView الموقّع من Telegram بعميل Telethon نفسه، ويستخرج tgWebAppData مرة واحدة دون فك ترميز متكرر. يرفض اختلاف bot_id أو نطاق التطبيق أو إعادة توجيه HTTP. لا تُرسل بيانات اعتماد Telegram إلى نطاق آخر ولا تُطبع في السجلات.

عقد الواجهة المتحقق منه: `POST bootstrap` بجسم bot_id وreset_view وdevice_language؛ ثم `POST action` بجسم bot_id وsession_id وaction_token وUUID request_id؛ ثم `POST status` بجسم bot_id وsession_id. لا يُضاف operation_id إلى الطلبات لأنه غير موجود في طلب status في المصدر. session_id وتوكنات الأزرار تحفظ داخل الذاكرة فقط.

الملاحة تستعمل الأزرار الفعلية ذات kind/context من أحدث بطاقة: trade_menu ثم assets لسوق o، ثم timeframes للزوج، ثم confirm للمدة، ثم signal. قائمة Currencies وOTC في الواجهة جزء من مرشحات المتصفح المحلية؛ في HTTP نختار من asset_catalog بالرمز والسوق نفسهما، دون الحاجة إلى نقر المرشحات المرئية. إذا كانت الإشارة النهائية على الزوج والمدة نفسيهما، يُستعمل زر kind=signal الجديد فقط؛ وإذا تغيرا يعاد مسار الاختيار. تُستعمل snapshot_seq لمنع التراجع داخل الجلسة وتُصفّر عند تغيّرها، كما في المصدر العام.

كل إشارة تحتاج بطاقة screen=signal مع busy=false واتجاهًا وحيدًا مطابقًا: BUY→UP وSELL→DOWN أو Meta Signal: Higher/Lower/Выше/Ниже. يتطلب القبول أيضًا عملية جديدة وهوية نتيجة مختلفة عن السابقة وتطابق symbol وmarket=o وtimeframe. الثقة والرصيد والوصول ليست اتجاهًا. إذا تغير شكل بطاقة المزود أو تعذر إثبات الجِدة، يتوقف المسار بدل التخمين.

هذا ليس تنفيذًا حرفيًا لزر الرجوع المرئي: النتيجة الوظيفية نفسها تتم عبر أزرار الخادم الرسمية التي تستعملها الواجهة العامة. ليست هناك إشارة مولدة محليًا، ولا تعديل للصلاحيات أو المستويات.

### 5. التعافي والتشخيص

توكنات الأزرار قدرات مبهمة صادرة عن المزود؛ لا تُختلق ولا يعاد استعمال توكن محفوظ. نرسل request_id كما يفعل التطبيق، لكن لا نعيد POST action الملتبس تلقائيًا حتى ولو كان UUID نفسه. في خطأ إرسال مبهم يظهر META_API_ACTION_UNCERTAIN وتتوقف الحلقة دون صفقة ودون طلب إشارة ثانية تلقائيًا. status وحده قابل لإعادة المحاولة المحدودة مع تأخير متزايد. 401/403 و429 وانتهاء الجلسة/الزر وأخطاء صلاحية الأصل/المدة نهائية لتلك الدورة، وليست حلقة إعادة طلب تستهلك الحصة.

عند الخطأ النهائي ينظف المستمع عميل HTTP والتوكنات من الذاكرة؛ Start لاحق بطلب منك يستطيع جلب رابط تطبيق جديد دون تبديل StringSession. لا يوجد ضمان بأن مجرد إعادة فتح التطبيق تلغي جلسة قديمة. عمر initData الفعلي يحدده تحقق خادم المزود، وليس مدة ثابتة نفترضها. لا تحاول معالجة خطأ مستوى الوصول بتغيير حساب المنصة أو بإيداع تلقائي.

### 6. الاختبارات وحدود الإثبات

المسار HTTP لا يحتاج Playwright. لاختبار كل المشروع بما فيه اختبارات v21 الأصلية الاختيارية:

```sh
pip install -r requirements-browser.txt
python -m playwright install --with-deps chromium
python -m unittest discover -s tests -v
```

لتشغيل اختبارات HTTP فقط، بعد المتطلبات الأساسية:

```sh
python -m unittest discover -s tests -p 'test_v22_http_api.py' -v
```

مصدر العقد العام الذي قُرئ أثناء هذا التعديل: https://sdasdsahdsa.lol/miniapp/assets/app.js?v=20261115.meta15.0-live6-grok-lang . راجع `verification.json` لبصمة هذا المصدر ونتائج الاختبار والملفات التي ظلت مطابقة للأرشيف المرفق. لا تُعد هذه الـAPI عامة موثقة أو ثابتة؛ تحديث المزود قد يستلزم تعديلًا، ولا نختبر باستخدام حساب المستخدم دون بيانات وصول مناسبة وتفويض واضح.

مسار المتصفح القديم باقٍ اختياريًا عند META_SIGNAL_BACKEND=browser، ويتطلب requirements-browser.txt وتثبيت Chromium، ولا ينطبق عليه حاجز الاختبار الخاص بمسار HTTP؛ لا تستخدمه أثناء فحص HTTP. META_SIGNAL_BACKEND=telegram هو المسار القديم للرسائل، وauto يحافظ على التوافق مع البوتات القديمة عند عدم وجود Mini App. على Render استخدم http صراحة لمنع الانتقال الصامت إلى مسار قديم.

**المخاطر:** لا يثبت وجود illustrative/simulated_wait أن كل إشارة عشوائية؛ لكنه مع نص المزود لا يثبت تحليلًا فعليًا أو احتمال ربح موثوقًا. لا نعامل free_remaining=3 بوصفه سقفًا مؤكدًا لحساب Pro المدفوع دون قاعدة صريحة من المزود. إشارات المصدر قد تخطئ وقد تفقد الصفقة كامل مبلغها؛ المضاعفات تزيد الخطر. لا يُسجَّل initData أو session_id أو operation_id أو action_token، ولم تُدمج قيم المستخدم الخاصة في المشروع.

# تعليمات الإصدارات السابقة — v20/v21 (مرجع تاريخي)

نسخة مبنية على أرشيف v19 المرفق. الإصلاحات في طبقات النقل والحماية والتشغيل والواجهة؛ ملفات إرسال/حسم الصفقة والمارتينغيل الأساسية لم تتغير. الاختبارات محاكاة محلية، وليست إثباتاً للتوافق مع جلسة المنصة الحية أو للربحية.

## النشر الآمن على Render

1. أوقف التداول من الكنترولر وانتظر حسم الصفقة المفتوحة.
2. استبدل مجلد المشروع كاملاً بمحتويات `po_autotrader`، بما فيه `assets/brand` والملفات الجديدة.
3. احتفظ بمتغيرات البيئة الموجودة وبنفس MongoDB؛ لا تنشئ قاعدة بديلة ولا تحذف الإحصائيات.
4. Build: `pip install -r requirements.txt`، Start: `python -u run.py`، Health: `/health`.
5. تحقق من `build=v20-payout-cycle-fix` ثم افتح `/start`. التداول لا يبدأ تلقائياً بعد إعادة النشر؛ اضغط Start بعد الفحص على PRACTICE.

لا توجد متغيرات بيئة جديدة مطلوبة. إعدادات الحدود والعائد والتشغيل/الراحة تحفظ في MongoDB. الجدولة معطلة افتراضياً للحسابات التي لم تضبطها؛ سياسة العائد والحدود القديمة لا تُمسح. ملفات الصور محلية لا تحتاج تحميل خارجي أو توليد جديد. `/health` يفحص حياة الخدمة و`/ready` يفحص جاهزية مالك قفل التشغيل. self-ping جهد مساعد وليس ضماناً لعدم تعليق الخطة المجانية أو بديلاً لخدمة متاحة باستمرار.

## إصلاح قراءة عائد الزوج

العائد هو بيانات أصل Pocket Option، وليس Accuracy من MetaTrading، ولا نسبة نجاح الصفقات. لا نفترض 92% ولا نستنتج العائد الحالي من صفقة قديمة.

- `wire_decoder.py`: يفك أحداث Socket.IO، المرفقات الثنائية، namespace/ack، JSON المباشر، بادئة Engine.IO الثنائية، وgzip/zlib مع حدود حجم. لا يسجل حزم الجلسة أو التوكن.
- `payout_guard.py`: يستقبل جداول وأغلفة بيانات متعددة، ويعزل PRACTICE عن REAL ويمنع العائد القديم أو الأصل المغلق. في مخطط الجدول المدعوم اسم الأصل في index 1 والعائد في index 5.
- قائمة أزمنة الصفوف في index 15 تُحفظ كبيانات وصفية وليست حظرًا مؤكداً على مدة 5 ثوانٍ. عند وجود خريطة عائد صريحة لكل مدة أو `supported_durations`، تُحترم ولا يُستعاض عن مدة مفقودة بمدة أخرى. العائد العام للزوج ليس ضماناً لعائد مختلف يخص مدة لم يرسلها المصدر صراحة.
- زر **جلب العائد من المنصة** يعيد الاتصال لجلب جدول جديد، لا يغير عمر بيانات قديمة ليجعلها حديثة. أثناء صفقة مفتوحة ينتظر التجديد حتى حد آمن بين الصفقات. غياب/تقادم البيانات يطلب تجديداً بمعدل محدود.
- لوحة الحماية تميز: لا اتصال، لم يصل جدول، الزوج غائب، قراءة قديمة، زوج مغلق، مدة غير مدعومة، قراءة حديثة. يظهر العائد المستلم وعمره؛ رؤية نسبة بجوار حالة قديمة لا تعني السماح بالدخول.
- زر **تشخيص القراءة** يعرض أعداد الأحداث والصفوف والأصول والمرفقات الناجحة/المرفوضة فقط، بلا بيانات اعتماد.

من الإعدادات → حماية عائد الزوج، اختر تعطيل / إيقاف عند الحد / تبديل الزوج. علامة ✅ تبين الوضع الحالي، وتظهر أرقام الحدود في الأزرار. مثال: الإجراء `≤85%` والبديل `≥92%`. إذا وصلت قراءة حديثة BHDCNY_otc بقيمة 65%، لا يدخل عليه مع حد 85%. لا نساوي BHD برمز آخر مكتوب يدوياً؛ نعتمد رمز الأصل الفعلي في الجلسة.

في STOP: عائد منخفض أو مجهول يوقف الدخول ويستلزم Start بعد معالجة السبب. في SWITCH: يبحث عن أعلى بديل حديث من القائمة المشتركة بين الكنترولر والمنصة وMetaTrading، ثم يختار نفس المدة ويؤكدها. إذا لم يوجد بديل مناسب يبقى بلا دخول. حداثة البيانات تفحص مجدداً قبل الإرسال. يتطلب عمل الحماية وصول جدول عوائد مدعوم من جلسة المنصة؛ الصور والسجلات القديمة لا تكفي لإثبات ذلك. عند استمرار NO_TABLE بعد النشر استخدم التشخيص، ولا تعطل الحماية على حساب حقيقي لتجاوز المشكلة.

## حدود الربح والخسارة

الإعدادات → حدود الربح والخسارة → تشغيل بحدود. أدخل حد الربح مثل 200 وحد الخسارة المرغوب. الحساب هو صافي الربح/الخسارة المسجل للحساب المختار منذ آخر تصفير، وليس مبلغ الرصيد أو هدفاً يبدأ تلقائياً من لحظة تفعيل الحد.

عند الصافي `>= +200` أو `<= -حد الخسارة` يُمنع الدخول التالي فور حسم النتيجة، حتى وسط سلسلة التدبيل. لا تنتظر الحدود المالية إكمال السلسلة، ولا تستأنفها نهاية الراحة. ليست هناك إمكانية لإلغاء صفقة قُبلت بالفعل من المنصة؛ لذلك يمكن تجاوز الحد بمقدار نتيجة الصفقة الأخيرة. النتائج المجهولة لا تُختلق كربح أو خسارة. للبدء بهدف جديد راجع الإحصائيات وحدودك؛ التصفير يزيل الإحصائيات فقط بعد تأكيد المستخدم.

## وقت التشغيل والراحة

الإعدادات → التشغيل والراحة:

- بدون وقت: السلوك التقليدي، مع استمرار حدود المال والعائد إن كانت مفعلة.
- توقف بعد المدة: إيقاف عند انتهاء وقت التشغيل وفق قاعدة إنهاء الصفقة/السلسلة؛ لا استئناف تلقائي. Start جديد يعيد بدء دورة وقت جديدة بعد فحص حدود المال.
- تشغيل وراحة: مثال 10 دقائق تشغيل و10 دقائق راحة، ثم استئناف تلقائي ما دام التشغيل لم يوقف يدوياً ولم يتحقق حد مالي.

المدد بالدقائق، وتوجد اختيارات سريعة وإدخال مخصص؛ المجال 0.01–10080 دقيقة. وقت التشغيل وقت حائط يشمل انتظار الإشارة والاتصال؛ ليس مجموع مدد الصفقات فقط. في قاعدة إكمال السلسلة قد يتجاوز التشغيل المدة المحددة حتى تنتهي السلسلة القائمة. لا يَعِد النظام بأن الاستراحة تحسن التحليل أو نسبة الفوز.

**قاعدة نهاية الوقت**:

- **أكمل السلسلة**: إذا انتهت 10 دقائق والبوت في التدبيلة الثانية/الثالثة/الرابعة، يكمل السلسلة الحالية حتى فوز أو استنفاد مستوياتها، ثم يبدأ الراحة. لا ينتظر كامل حملة التعزيز التي قد تضم سلاسل متعددة. تبقى حدود المال والعائد وStop أعلى أولوية، وقد تمنع إكمال السلسلة.
- **الصفقة فقط**: يحسم الصفقة المفتوحة ثم يستريح، ويحافظ على مستوى التدبيل التالي للاستئناف. هذا الخيار لا يضيف راحة بعد كل خسارة ما لم يكن وقت التشغيل قد انتهى.

خلال الراحة لا تُفتح صفقات ولا تُستعمل إشارة قديمة عند العودة. تظل الجلسة وواجهة التحكم متاحتين قدر الإمكان. Stop أثناء الراحة يلغي الاستئناف. الجدول وموعد نهاية التشغيل/الراحة محفوظان بكتابة مشروطة في MongoDB؛ تعديل الإعدادات يعيد تهيئة ساعة الدورة ولا يمس صافي الربح أو التعزيز. بعد إعادة نشر الخدمة لا يبدأ التداول دون أمر المستخدم، وإن بقيت حالة الدورة محفوظة.

الأولوية: Stop/فقد ملكية MongoDB → الحدود المالية → حظر العائد/الاختيار غير المتزامن → وقت التشغيل والراحة → الدخول. لا يؤدي تشغيل خيار زمني وحده إلى إرسال صفقة دون Start.

## الاتصال والسجلات

`TelegramNetworkError: ServerDisconnectedError` خطأ شبكة في Bot API، وليس دليلاً بمفرده على سبب فقدان جدول العوائد. aiogram يعيد محاولة getUpdates تلقائياً؛ أضيفت محاولة بدء آمنة لـ deleteWebhook/getMe مع تدرج انتظار قابل للإلغاء عند الإغلاق. التوكن غير الصحيح والأخطاء الدائمة لا تعامل كأخطاء شبكة عابرة. لا نعيد إرسال أمر تداول بعد خطأ شبكة مبهم، تفادياً لصفقتين.

سجلات طبقات النقل والعائد والجدولة والواجهة والعامل تحمل أجزاء الثانية، وسجل المحرك الأصلي احتفظ بتوقيته. تظهر standby أثناء انتقال Render بين نسختين؛ لا يبدأ polling أو التداول في النسخة الجديدة حتى تملك قفل MongoDB. لا تُشغّل نسختين مستقلتين بنفس التوكن وقواعد بيانات مختلفة. عند فقد القفل يتوقف الدخول وتغلق الخدمة بأمان قدر مهلة المنصة. انقطاع الشبكة قد يبقى ممكناً؛ لا يدّعي الإصدار إزالة انقطاعات Telegram/Render الخارجية.

## الحفاظ على السلوك السابق

ملفات `pocket_option.py`, `martingale.py`, `telegram_signal.py`, `logger.py` متطابقة مع v19. الإحصائيات والتعزيز وصور البراند ومزامنة MetaTrading محفوظة. التغييرات الجديدة في ملفات طبقات التحكم/النقل والمخطط وقاعدة البيانات والتكامل الضروري للعامل. معالجة الإشارات تدعم Meta Signal/Higher/Lower وDirection/UP/DOWN كما سبق.

مسار رسائل تيليجرام القديم، عند توفره: Trade → OTC → الزوج → المدة → Confirm، ثم أول إشارة جديدة وNew signal. لمسار Beta App الجديد راجع القسم التالي. تغيير الزوج/المدة لا ينقل نتيجة الصفقة المفتوحة إلى الزوج الجديد. لا تجاوز للتحقق من تطابق الزوج والمدة قبل الدخول.

## الاختبارات وحدود التحقق

شغل من مجلد المشروع: `python -m unittest discover -s tests -v`.

تشمل الاختبارات مخططات العائد، حزم المرفقات، فصل الحسابات، البيانات القديمة، التحويل التلقائي، حدود المال، دورة تشغيل/راحة بساعة افتراضية، إكمال 1/2/4/8 قبل الراحة، استئناف المستوى المحفوظ، إيقاف أثناء الراحة، هجرة MongoDB، وبدء تيليجرام بعد انقطاع عابر. راجع `verification.json` لعدد الاختبارات وبصمات النواة.

لم تُستخدم بيانات اعتماد المستخدم ولم تُفتح صفقة حية أثناء التطوير. نجاح الاختبارات ليس ضماناً لعدم ظهور مخطط منصة آخر، ولا ضماناً لعدم انقطاع الشبكة، ولا للربح. ابدأ بـ PRACTICE وتحقق من العائد المعروض مقابل المنصة لنفس الحساب والزوج والمدة قبل REAL. المضاعفات والتعزيز تزيد المخاطر وقد تستنفد الرصيد.

مرجع مخطط الجدول الذي روجع: https://github.com/ChipaDevTeam/PocketOptionAPI/blob/main/pocketoptionapi_async/websocket_client.py
وثائق نشر Render: https://render.com/docs/deploys

## تحديث v21: مصدر الإشارات داخل Beta App

أضيف `meta_webapp.py` للتعامل مع Mini App من خلال متصفح Chromium. يحصل على رابط فتح التطبيق من زر Beta App الفعلي أو قائمة البوت باستخدام عميل Telethon القائم وجلسة المستخدم نفسها؛ لا ينشئ جلسة تيليجرام جديدة ولا يعدل StringSession أو بيانات المنصة أو قاعدة البيانات. لا يخمّن مسارات API خاصة بمصدر الإشارات، ولا يخزن رابط المصادقة في السجلات أو ملفات المتصفح.

عند فتح التطبيق على شاشة الإعدادات المحفوظة، يرجع بزر الرجوع داخل التطبيق (أو BackButton الخاص بـ Telegram، وليس إغلاق WebView)، ثم Start → Currencies → OTC → الزوج المحدد في لوحة التحكم → المدة → Get signal. عند تطابق الزوج والمدة وبقاء بطاقة الإشارة النهائية، يستعمل New signal فقط. تغيير أي منهما يعيد مسار الاختيار. Higher تصبح UP وLower تصبح DOWN عبر واجهة التحليل الأصلية. لا تؤخذ الثقة/الدقة بوصفها اتجاهًا.

قبل قبول البطاقة، يشترط رصد مرحلة التحليل بعد الطلب الحالي، ثم SIGNAL READY واتجاهًا واحدًا وتطابق الزوج والمدة. لا يستخدم بطاقة قديمة لمجرد ظهور New signal. المدد المقفلة مثل S5/S15/S30 لا تستبدل تلقائياً بدقيقة؛ إن لم تتوفر المدة يتوقف طلب الإشارة ولا ينفذ على مدة مختلفة. لم نغيّر الإعداد الافتراضي المخزن للمدة؛ اختر M1/60 ثانية بنفسك إن كان هذا هو المطلوب والمتاح.

### تثبيت المتصفح والنشر

على Render: أبقِ جميع التوكنات وTELEGRAM_STRING_SESSION وSSID وMONGO_URI وأمر التشغيل `python -u run.py` كما هي. احتفظ بـ SIGNAL_BOT_USERNAME لاسم مصدر الإشارات الصحيح؛ إن تغير اسم المصدر، حدّث هذا المتغير وحده إلى الاسم الذي تملكه، إذ لم يظهر اسم المستخدم الجديد في الفيديو ولم يُخترع اسم بديل.

عند استخدام Blueprint، يتضمن render.yaml تثبيت Chromium وPLAYWRIGHT_BROWSERS_PATH=0. أما خدمة Render الموجودة والمضبوطة يدوياً، فلا يكفي رفع render.yaml: أضف متغير البيئة `PLAYWRIGHT_BROWSERS_PATH=0` وعدّل Build Command إلى:

```sh
pip install -r requirements.txt && python -m playwright install chromium
```

ثم أعد النشر. لا تضع القيمة 0 بعد بناء المتصفح في مسار مختلف؛ استخدم المتغير نفسه وقت البناء والتشغيل. يتطلب Chromium أيضاً مكتبات نظام Linux. إذا اشتكى السجل من مكتبة مشتركة مفقودة فلا تُنشئ جلسة تيليجرام جديدة؛ ثبّت متطلبات النظام في بيئة تسمح بذلك (`python -m playwright install-deps chromium` بصلاحيات مناسبة)، أو استخدم بيئة Docker الداعمة لـ Playwright. لا يدّعي هذا التعديل تثبيت حزم نظام على خدمة لا تمنح صلاحية ذلك. يحتاج المتصفح ذاكرة إضافية مقارنة بمسار رسائل تيليجرام وحده.

للتشغيل المحلي بعد `pip install -r requirements.txt`:

```sh
python -m playwright install chromium
python -m unittest discover -s tests -v
```

مرجع تثبيت المتصفح ومكتبات النظام: https://playwright.dev/python/docs/browsers

### نطاق التعديل وحدود التحقق

لم يتغير `meta_navigation.py` أو `telegram_signal.py` أو ملفات اتصال المنصة والجلسات والتدبيل والإحصائيات/الجدولة. تغير ربط مصدر الإشارة في `synchronized_signals.py`، وأضيف في `worker.py` تنظيف موارد المتصفح عند إغلاق العامل أو استبدال مستمع الإشارات، دون تغيير منطق الدخول أو المصادقة. أضيف اعتماد Playwright ومتطلبات بناء Chromium، واختبارات المتصفح. قارن `verification.json` ببصمات الملفات في الأرشيف الأصلي.

الاختبارات الجديدة تشغّل Chromium فعلياً على واجهة محلية محاكية للخطوات المرئية في الفيديو، وليست على التطبيق الحقيقي. لا يحتوي الأرشيف على DOM التطبيق الجديد أو رابطه المصادق عليه، ولم تتوفر جلسة مخوّلة لاختباره حياً؛ لذلك لا يمكن تأكيد توافق كل محدد DOM مع واجهة المزود الفعلية من الفيديو وحده. لا يشكل نجاح الاختبارات ضمان تشغيل حي أو ضمان ربح. ابدأ بـ PRACTICE وزوج OTC متاح ومدة M1، وتحقق من دورة Get signal ثم تكرار New signal وتغيير الزوج قبل أي استخدام حقيقي. عند عدم التعرف على الشاشة أو الزوج/المدة، لا يخمّن الاختيار ولا يرسل صفقة استنادًا إلى هذه الحالة.
